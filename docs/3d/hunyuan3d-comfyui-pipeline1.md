# Hunyuan3D ComfyUI Workflow Reconstruction

## High-Level Pipeline Overview

The attached graph is not a pure Hunyuan3D 2.1 workflow in the strict model-version sense. The saved ComfyUI graph loads a multiview **v2.0/v2mv** shape checkpoint (`hunyuan3d-dit-v2-0-mv-fast-fp16.safetensors`), the **v2.0 Delight** model, and the **v2.0 Paint** model, while the provided entity["company","GitHub","code hosting platform"] repo from `visualbruno/ComfyUI-Hunyuan3d-2-1` targets the newer 2.1 wrapper family. Architecturally, though, they are close enough to map cleanly: shape first, then mesh-conditioned multiview texturing, then baking, inpainting, and export. fileciteturn0file0 citeturn27search0turn28search1turn35search2

At the model level, this is a **two-stage, diffusion-guided image-to-3D pipeline** in the same overall sense described by entity["company","Tencent","technology company"]: a shape model generates 3D geometry, and a separate paint model generates texture conditioned on mesh-derived geometric priors. The workflow is specifically a **multi-view-conditioned shape diffusion + mesh-conditioned multi-view texture diffusion + UV bake/inpaint** system. It is **not** classical multiview stereo, photogrammetry, or a NeRF pipeline; it uses learned generative priors for both geometry and texture. citeturn30search2turn28search0turn28search2

Conceptually, the pipeline runs in the following order:

Input views are normalized and background-cleaned, a multiview Hunyuan3D shape model infers a 3D latent, and a VAE-style decoder turns that latent into a mesh. The mesh is then UV-unwrapped, rendered into normal and position maps from a fixed six-camera rig, and passed into Hunyuan3D-Paint to synthesize view-consistent texture images. Those synthesized views are then baked back into texture space, repaired with geometry-aware and image-space inpainting, attached to the mesh, and exported as a GLB. The graph also exports an earlier untextured GLB for inspection. fileciteturn0file0 citeturn30search2turn11view0turn9view1turn9view2

In terms of named Hunyuan3D subsystems, the graph uses **Mesh/Shape** for geometry generation, **Delight** as appearance preprocessing, and **Paint** for multiview texture synthesis. It does **not** use the newer 2.1 high-level PBR path end to end; the workflow’s texturing branch is still the older RGB/albedo-style Hunyuan3D-Paint flow rather than the full 2.1 albedo + metallic/roughness material pipeline. fileciteturn0file0 citeturn28search1turn17view2turn19view1turn11view0

## Node Graph to Functional Blocks

Before mapping stages, it helps to define the payloads moving through the graph. In these wrappers, `IMAGE` is represented as a batched float tensor in ComfyUI’s usual NHWC style and gets permuted to NCHW before model calls; helper functions convert between PIL and normalized float tensors. `MASK` is a single-channel float mask, often carried with singleton batch or channel dimensions depending on the node. `HY3DLATENT`, `HY3DMODEL`, `HY3DVAE`, `TRIMESH`, and `MESHRENDER` are opaque custom objects: respectively a shape latent, a shape pipeline handle, a decoder handle, a `trimesh` mesh object, and a stateful renderer/baker object. citeturn12view3turn20view2turn20view3

**Input preparation.** The graph’s front/left/right/back branches load four source images, resize them to **518×518**, remove the background, invert the resulting masks, and then reattach alpha with `JoinImageWithAlpha`. The relevant nodes are `LoadImage` (157, 160, 167, 159), `ImageResize+` (52, 171, 172, 176), `TransparentBGSession+` (55), `ImageRemoveBackground+` (56, 170, 173, 177), `InvertMask` (202, 199, 200, 201), and `JoinImageWithAlpha` (195, 196, 197, 198). The flowing data is `IMAGE → MASK → IMAGE-with-alpha`, and the purpose is to hand the shape model tightly cropped, object-centric views with consistent framing. The workflow note explicitly says the 518 size is tied to the image encoder, and that the alpha-join path is unnecessary if the input is already background-removed or RGBA. fileciteturn0file0 citeturn28search0turn34search1

**Mesh generation.** `Hy3DModelLoader` (10) loads the shape pipeline and VAE. `Hy3DGenerateMeshMultiView` (166) receives the four prepared `IMAGE` views and emits a `HY3DLATENT` plus an auxiliary `IMAGE` and `MASK`. `Hy3DVAEDecode` (140) turns the latent into a `TRIMESH`, and `Hy3DPostprocessMesh` (203) cleans it before the graph branches to untextured export (`Hy3DExportMesh` 17), single-view preview (`Hy3DRenderSingleView` 163), and UV/texturing. This stage exists because Hunyuan3D decouples geometry from texture: the mesh must exist before any mesh-conditioned rendering or paint diffusion can happen. fileciteturn0file0 citeturn30search2turn28search0turn10view1turn10view2

**Delight-based appearance cleanup.** The graph takes the auxiliary `IMAGE`/`MASK` from `Hy3DGenerateMeshMultiView`, composites the image over a repeated gray background built from `SolidMask` (132), `MaskToImage` (133), `RepeatImageBatch` (184), and `BatchCount+` (185), then runs `Hy3DDelightImage` (35) using the model loaded by `DownloadAndLoadHy3DDelightModel` (28) and the scheduler from `Hy3DDiffusersSchedulerConfig` (148). The payloads are `IMAGE + MASK → composited IMAGE → delighted IMAGE`. This step exists to remove illumination and shadow bias before the image is reused as the paint model’s reference condition. The workflow note explicitly warns that background level affects delighting, which is why the graph inserts a controlled gray backing instead of feeding a hard alpha cutout directly. fileciteturn0file0 citeturn17view2turn18view0turn19view1

**UV wrapping and geometry rendering.** `Hy3DMeshUVWrap` (83) takes the cleaned `TRIMESH` and creates a UV layout. `Hy3DCameraConfig` (61) defines the six camera views, and `Hy3DRenderMultiView` (79) renders the UV-wrapped mesh into `normal_maps`, `position_maps`, and a persistent `MESHRENDER` object. The workflow uses render size **1024**, texture size **2048**, and `normal_space="world"`. The data flow is `TRIMESH → UV-wrapped TRIMESH → IMAGE batches + MESHRENDER`. This stage exists because Hunyuan3D-Paint is not fed a raw mesh directly from ComfyUI; instead, it is conditioned by rendered geometric cues that tell the diffusion model where surface orientation and spatial position lie in each view. fileciteturn0file0 citeturn10view3turn18view2turn20view0turn30search2

**Diffusion-based multiview enhancement.** `DownloadAndLoadHy3DPaintModel` (85) loads the texture diffusion pipeline, `Hy3DDiffusersSchedulerConfig` (149) builds a scheduler, and `Hy3DSampleMultiView` (88) combines the delighted reference image, the rendered normal maps, the rendered position maps, and the six-view camera config to synthesize a batch of texture views. The graph uses **view size 512**, **25 sampling steps**, and **denoise strength 1.0**; the optional latent `samples` input is left empty. The output is a batch of `IMAGE`s, previewed by node 111. This step exists because the workflow generates appearance in **image space first**, where the paint diffusion model is strongest, and only later consolidates those images into UV space. fileciteturn0file0 citeturn19view1turn31view2turn39view0turn39view1

**Texture baking and refinement.** After sampling, the graph upsizes those synthesized views with `ImageResize+` (117) to **2048×2048** before baking; a model upscaler path (`ImageUpscaleWithModel` 118, `UpscaleModelLoader` 119) is present but muted. `Hy3DBakeFromMultiview` (92) projects the multiview images back into texture space, yielding a `texture` `IMAGE`, a `mask`, and the forwarded `renderer`. `Hy3DMeshVerticeInpaintTexture` (129) then uses the mesh itself to fill texture holes, and `CV2InpaintTexture` (104) performs a last 2D cleanup. The data flow is `IMAGE batch + MESHRENDER + HY3DCAMERA → baked texture IMAGE + MASK → repaired texture IMAGE`. This block exists because diffusion produces view images, not a complete seam-free UV atlas; bake and repair are what convert those views into a usable texture map. fileciteturn0file0 citeturn20view2turn20view3turn27search0

**Final mesh application and export.** `Hy3DApplyTexture` (98) maps the repaired texture back onto the mesh carried by `MESHRENDER`, producing a textured `TRIMESH`. `Hy3DExportMesh` (99) writes the textured result as a GLB, and `Preview3D` (154) previews it. In parallel, node 17 already exported the intermediate untextured mesh. This stage exists because baking and inpainting still live in texture space; they only become a finished asset once that image is attached to the geometry and serialized into a mesh format with UV/material data. fileciteturn0file0 citeturn38search0turn37search0

## Deep Dive Into the Custom Nodes

The exact node names in the saved JSON belong to the earlier Hunyuan3DWrapper family, while the provided visualbruno 2.1 repo reorganizes some of the same logic into newer classes such as `Hy3D21VAEDecode`, `Hy3DMultiViewsGenerator`, `Hy3DBakeMultiViews`, and `Hy3DInPaint`. That means the most accurate reconstruction is a hybrid one: use the provided 2.1 repo for the modern equivalents and the older wrapper code for the exact v2.0 node classes that still appear in the workflow. fileciteturn0file0 citeturn27search0turn11view0turn9view1turn9view2

**Hy3DGenerateMeshMultiView.** Functionally, this node wraps the multiview Hunyuan3D shape generator. The official Hunyuan3D-2mv model card shows the underlying API takes an `image` dictionary keyed by `front`, `left`, `back`, and `right`, and the provided visualbruno repo still contains a commented multiview shape-generator stub that converts each input `IMAGE` to PIL, builds a `view_dict`, and calls `Hunyuan3DDiTFlowMatchingPipeline(..., image=view_dict, num_inference_steps=steps, guidance_scale=guidance_scale, generator=torch.manual_seed(seed))`. In the graph, its visible inputs are `HY3DMODEL + front IMAGE + left IMAGE + right IMAGE + back IMAGE`, and its outputs are `HY3DLATENT + IMAGE + MASK`. The hidden assumption is strict canonical view semantics: “front” must really be front, “left” and “right” must be true orthogonal sides, and object scale/background should be well normalized across views. fileciteturn0file0 citeturn28search0turn13view0turn36view0

**Hy3DVAEDecode.** The 2.1 equivalent is explicit in the provided repo: it moves the VAE to device, optionally enables FlashVDM decoding, decodes the incoming latent token set with `vae.decode(latents)`, then converts the decoded field to mesh geometry using `vae.latents2mesh` with `bounds=box_v`, `mc_level`, `num_chunks`, `octree_resolution`, and `mc_algo`. After extraction, it flips triangle winding with `outputs.mesh_f = outputs.mesh_f[:, ::-1]` and constructs a `trimesh` object. In the saved graph, the user-facing controls are `box_v=1.01`, `octree_resolution=256`, `num_chunks=32000`, `mc_level=0`, and `mc_algo="mc"`. The latent tensor shape is not surfaced in the ComfyUI port, but the VAE config used in the wrapper strongly suggests a set-style latent structure rather than a 2D image latent; in the earlier loader code that configuration is `num_latents=3072` and `embed_dim=64`, so an internal shape like `[B, 3072, 64]` is a reasonable inference. fileciteturn0file0 citeturn10view0turn10view1turn17view1turn37search2

**Hy3DRenderMultiView.** This node wraps the differentiable `MeshRender` object. The older wrapper code shows that it instantiates `MeshRender(default_resolution=render_size, texture_size=texture_size, camera_distance=camera_distance, ortho_scale=ortho_scale)`, loads the mesh, and renders batches of normal and position maps over the selected camera set. In `world` mode, it uses absolute-coordinate normals; in `tangent` mode, it remaps the normal tensor from `[0,1]` to `[-1,1]`, normalizes it, and flips the Z axis to standard normal-map convention. The output tensors are batched `IMAGE`s plus the persistent `MESHRENDER` object and optional masks. The hidden assumptions are that the mesh is already centered and scaled into the renderer’s expected camera framing, and that the chosen camera parameters are close to the training rig the paint model expects. fileciteturn0file0 citeturn14view2turn18view2turn20view0

**Hy3DSampleMultiView.** This is the core texture-view generator. The paint model loader in the older wrapper builds a `HunyuanPaintPipeline` from a `UNet2p5DConditionModel`, `AutoencoderKL`, CLIP text encoder, tokenizer, scheduler, and image processor, then optionally compiles or CPU-offloads it. The sampling node takes the delighted `ref_image`, batched `normal_maps` and `position_maps`, and a camera config; converts the geometry controls to PIL images; resizes them to `view_size`; constructs a discrete `camera_info` code list from azimuth/elevation; and finally calls the pipeline with `num_in_batch=num_view`, `camera_info_gen=[camera_info]`, `camera_info_ref=[[0]]`, `normal_imgs`, `position_imgs`, `num_inference_steps=steps`, and optional starting latents plus `denoise_strength`. The output is a multiview image batch in NHWC float format. Two hidden assumptions matter here: the camera angles are not treated as arbitrary continuous metadata but as indices into a fixed training-time camera codebook, and the reference image is anchored to reference camera index `0`, which effectively makes the front view the canonical appearance anchor. fileciteturn0file0 citeturn17view2turn19view1turn31view0turn31view2turn39view0

**Hy3DBakeFromMultiview.** The older wrapper exposes this most clearly. It takes the sampled `IMAGE` batch, permutes NHWC to NCHW, converts each view into PIL, then for each `(view, elevation, azimuth, weight)` tuple calls `renderer.back_project(...)`. Each projected cosine-confidence map is reweighted as `weight * (project_cos_map ** bake_exp)` with `bake_exp = 4`, and then the renderer merges these projections using `fast_bake_texture`. The node returns a baked `texture`, a validity `mask`, and the forwarded `renderer`. Algorithmically, this is not diffusion anymore; it is weighted geometric reprojection into UV space. Its hidden assumptions are that the view order exactly matches the camera config and that regions with low cosine confidence or no visibility will remain weakly covered and need later repair. fileciteturn0file0 citeturn20view2turn20view3

**Hy3DMeshVerticeInpaintTexture.** This node is geometry-aware texture repair. It queries the renderer for `vtx_pos, pos_idx, vtx_uv, uv_idx`, converts the texture and mask into NumPy arrays, and calls `meshVerticeInpaint(texture_np, mask_np, vtx_pos, vtx_uv, pos_idx, uv_idx)`. That is a fundamentally different operation from flat 2D inpainting: it can use mesh adjacency and shared vertex/UV structure to propagate plausible color into UV holes that correspond to connected 3D surface regions. The node rewraps the result into float tensors and preserves the same `renderer` handle. The hidden assumption is that the UV atlas and topology are coherent enough that vertex-based propagation is meaningful. fileciteturn0file0 citeturn20view3

**Hy3DApplyTexture.** This exact class is not exposed in the provided visualbruno 2.1 repo, but the workflow’s type signature is unambiguous: it consumes an `IMAGE` texture and a `MESHRENDER` object and emits a textured `TRIMESH`. In system terms, it is the materialization node that takes the final UV texture image and binds it back to the mesh state already held by the renderer, producing a mesh object that can be exported. Because `Hy3DBakeFromMultiview` and `Hy3DMeshVerticeInpaintTexture` both preserve the renderer, `Hy3DApplyTexture` can assume UV layout, mesh indices, and rasterizer-space conventions are unchanged from the bake stage. The important hidden dependency is this renderer continuity: if you swap the renderer or UV layout between bake and apply, the texture will no longer align. fileciteturn0file0 citeturn38search0

**Hy3DDelightImage.** The delight model loader wraps a `StableDiffusionInstructPix2PixPipeline`, replaces its scheduler with `EulerAncestralDiscreteScheduler`, and either compiles or enables CPU offload. The node itself permutes each `IMAGE` batch to NCHW, resizes with `common_upscale`, and runs the pipeline with an empty text prompt, `image_guidance_scale=cfg_image`, `num_inference_steps=steps`, and a tiny text `guidance_scale` shim (`1.0` when `cfg_image==1.0`, otherwise `1.01`) so that the operation is essentially image-guided relighting cleanup rather than text-driven editing. It processes each image independently and returns a new batched `IMAGE` tensor. The hidden assumption is that the model is being asked to remove lighting/shadow bias while preserving object identity; if the input background or mask is unstable, delighting can hallucinate or wash out edges. fileciteturn0file0 citeturn17view2turn18view0turn19view1

## Data Flow Trace

Take one four-view object sample through the graph. First, the four source images are loaded as `IMAGE` tensors, resized to 518×518, background-removed into `MASK`s, and converted into alpha-bearing images through invert-and-join operations. Those prepared views feed `Hy3DGenerateMeshMultiView`, which packages them into a multiview condition for the Hunyuan3D-2mv shape model and emits a `HY3DLATENT`. That latent is still an opaque learned 3D representation, not a mesh. `Hy3DVAEDecode` then decodes it into a field representation and extracts a `TRIMESH` with marching cubes at octree resolution 256; `Hy3DPostprocessMesh` removes floaters and degenerate faces and reduces the face count cap to 50,000. At that point the graph exports an intermediate white/untextured GLB and also renders a single debug normal view for human inspection. fileciteturn0file0 citeturn28search0turn10view1turn10view2turn38search4turn37search1

Separately, the same `Hy3DGenerateMeshMultiView` node also emits an auxiliary `IMAGE` and `MASK`. The graph composites that image over a controllable gray background and passes it through `Hy3DDelightImage`, producing a lighting-flattened reference image batch. This is critical: the paint stage is **not** conditioned directly on the original four source views. Instead, it is conditioned on one canonical, delighted appearance reference plus rendered geometry from the mesh itself. That delighted `IMAGE` becomes the `ref_image` input to `Hy3DSampleMultiView`. fileciteturn0file0 citeturn36view0turn19view1turn31view2

The cleaned `TRIMESH` then goes through `Hy3DMeshUVWrap`, giving it UV coordinates. `Hy3DRenderMultiView` uses the six-camera rig from `Hy3DCameraConfig` to render batched `normal_maps` and `position_maps`, and it also returns a persistent `MESHRENDER` object that now “knows” the mesh, UV atlas, camera settings, and texture size. `Hy3DSampleMultiView` takes the delighted reference image, these geometric maps, the camera config, the paint diffusion pipeline, and the scheduler, maps the continuous angles onto the paint model’s discrete camera code system, and synthesizes a batch of texture views. Those images are still ordinary 2D views of the mesh, not yet a UV texture. fileciteturn0file0 citeturn10view3turn18view2turn31view0turn31view2turn39view0

Those synthesized views are then resized to 2048×2048 and fed into `Hy3DBakeFromMultiview`, which back-projects each image into the UV atlas using the renderer and camera metadata, combining them into a single baked `texture` plus a `mask` that marks missing or weakly trusted texels. `Hy3DMeshVerticeInpaintTexture` uses mesh topology to fill some of those holes in a surface-aware way, and `CV2InpaintTexture` fills the remaining 2D gaps. `Hy3DApplyTexture` then attaches that final texture image back to the renderer’s mesh state and emits a textured `TRIMESH`, which `Hy3DExportMesh` serializes to a GLB and `Preview3D` displays. The end result is therefore: **four input images → shape latent → mesh → rendered geometric controls → diffused multiview textures → baked UV texture → repaired texture → textured GLB**. fileciteturn0file0 citeturn20view2turn20view3turn38search0turn37search0

## Camera System and Multi-View Logic

The camera rig is one of the most important hidden mechanics in this workflow. `Hy3DCameraConfig` in the graph uses azimuths `[0, 90, 180, 270, 0, 180]`, elevations `[0, 0, 0, 0, 90, -90]`, weights `[1, 0.1, 0.5, 0.1, 0.05, 0.05]`, camera distance `1.45`, and orthographic scale `1.2`. That means the texture stage works with **six** synthetic views, not four: four cardinal equatorial views plus top and bottom views with small weights. Even though geometry is reconstructed from front/left/right/back inputs, texturing uses a richer virtual camera set to cover the mesh more completely. fileciteturn0file0 citeturn15view3turn9view3

`Hy3DRenderMultiView` uses the full camera config, including distance and ortho scale, when it creates the `MeshRender` object and renders normals/positions. `Hy3DSampleMultiView`, however, only consumes azimuths and elevations directly. It converts each angle pair to a discrete integer camera code through a lookup-and-binning formula, then passes those codes into the paint diffusion pipeline as `camera_info_gen`. That means there is an implicit training prior: the paint model expects views drawn from a fixed camera vocabulary rather than arbitrary continuously parameterized cameras. If you change azimuth/elevation modestly within that codebook, things still line up; if you change distance/scale aggressively, the renderer can drift away from what the diffusion model’s camera encoding implicitly expects. citeturn18view2turn31view0turn31view2

View consistency is maintained in three different ways at once. First, all renders come from a **single mesh**, so geometry is globally consistent by construction. Second, `Hy3DSampleMultiView` generates all target views together in one call with `num_in_batch=num_view`, shared camera metadata, and shared geometric controls, which is much stronger than generating each view independently. Third, baking uses view weights and cosine-confidence weighting, so the final UV atlas trusts the most front-facing, best-supported observations instead of averaging all views equally. In this graph, the front view is heavily favored, which is consistent with the paint sampler’s `camera_info_ref=[[0]]` convention and with the fact that the delighted reference image acts as a single canonical appearance anchor. fileciteturn0file0 citeturn31view2turn20view2turn20view3

## Texture Generation Strategy

This workflow uses a deliberately hybrid strategy: it **generates texture evidence in image space**, then **consolidates it into UV space**, then **repairs the UV texture with two different inpainting approaches**. That is more robust than trying to generate a UV map directly from the prompt or from the source photos, because the diffusion model can work in the natural image domain while the renderer enforces geometric correspondence later. This is exactly aligned with Hunyuan3D’s two-stage design, where texture synthesis is decoupled from shape generation and is driven by geometric priors instead of being solved jointly with mesh topology in one monolithic pass. citeturn30search2turn28search1turn29search2

The first texture pass is **multiview diffusion**. `Hy3DSampleMultiView` takes one delighted appearance reference, plus six rendered normal and position maps, and predicts a set of view-consistent images. These are not yet UV textures. The second pass is **baking**. `Hy3DBakeFromMultiview` back-projects those images into the UV atlas, weighting views by both user-specified confidence and local view angle. The third pass is **repair**. `Hy3DMeshVerticeInpaintTexture` works in a mesh-aware way to spread colors across connected surface neighborhoods, while `CV2InpaintTexture` patches whatever remains as a plain 2D image completion problem. fileciteturn0file0 citeturn31view2turn20view2turn20view3

Multiple passes are needed because each pass solves a different failure mode. Diffusion is good at plausible view images but does not guarantee UV completeness. Baking is good at geometric reprojection but leaves holes where no view saw a texel clearly enough. Vertex inpaint is good at propagating along actual surface connectivity, especially near seams and thin structures. CV2 inpaint is good at cheap cleanup of small residual gaps in flat texture space. If you remove any one of these stages, the most common failure shifts rather than disappears: skipping diffusion hurts realism, skipping bake leaves you without a UV map, skipping vertex inpaint leaves seam and topology-aware gaps, and skipping 2D inpaint leaves final pinholes or masked islands. fileciteturn0file0 citeturn20view2turn20view3turn30search1

## Key Insights and Non-Obvious Mechanics

The biggest non-obvious point is that **delighting happens before paint diffusion, but after shape generation**. In this graph, `Hy3DDelightImage` is fed from the auxiliary `IMAGE`/`MASK` output of `Hy3DGenerateMeshMultiView`, not from the original front/left/right/back source images. So the shape stage first reduces multiview appearance into one canonical image-like condition, and only then does the pipeline remove lighting from that canonical reference before texturing. This design makes sense if the author wants the paint model to see one clean “identity/appearance anchor” instead of four potentially inconsistent lit photographs. fileciteturn0file0 citeturn36view0turn19view1turn31view2

Another key mechanic is that **mesh comes before texture for structural reasons, not just workflow convenience**. The paint model needs rendered normal and position maps from the actual mesh to generate coherent views, and the bake step needs UVs plus a differentiable renderer to project those views into texture space. In other words, the geometry branch is not merely producing something to texture later; it is creating the geometric control signals that make the diffusion texture branch stable in the first place. That is why this pipeline is stronger than a naïve “paint directly from photos” setup. citeturn30search2turn18view2turn31view2turn20view2

UV wrapping is similarly non-optional. `Hy3DMeshUVWrap` is not a cosmetic preprocessing step; it is what creates a parameterization that `Hy3DBakeFromMultiview` can target. Without UV coordinates, there is nowhere to accumulate the back-projected texture evidence, no texture validity mask to inpaint, and no coherent texture image for `Hy3DApplyTexture` to attach. In the newer 2.1 code, this logic becomes even more explicit because the higher-level paint pipeline bundles unwrap, paint, bake, and inpaint into a more integrated material-generation flow. fileciteturn0file0 citeturn10view3turn11view0turn9view1turn9view2

Artifacts are most likely introduced in four places. The first is **view inconsistency at shape input**: if the supplied front/left/right/back do not really match or have different silhouettes, geometry can become lopsided or duplicated. The second is **UV seams and chart distortion** introduced by unwrapping. The third is **grazing-angle and occlusion loss** during bake, which is why the cosine-weighted trust mask exists. The fourth is **over-aggressive inpainting**, especially when large texture regions were never observed. The workflow notes also indicate that delighting is sensitive to the background level, which means poor alpha edges or bad background compositing can propagate all the way into texture generation. fileciteturn0file0 citeturn20view2turn20view3turn30search1

There is also a saved-graph quirk worth calling out. Although the workflow is conceptually a four-view setup, the attached JSON stores the right-view helper branch in a muted/disabled state (`mode=2` on the right `LoadImage`, resize, rembg, mask invert, and alpha-join helpers), and that branch points to the same example filename as the left view. So the graph topology reserves a `right` slot and `Hy3DGenerateMeshMultiView` still has a `right` input, but the specific saved example should be audited before treating it as a clean canonical four-view benchmark. fileciteturn0file0

## Optimization Opportunities

The clearest quality win is to revisit the **shape checkpoint and decode settings**. The saved graph is using the **fast** multiview checkpoint and decodes at octree resolution **256**; that is a pragmatic speed choice, not the quality ceiling. Moving from the fast checkpoint to the fuller 2mv model family, increasing `octree_resolution` toward 384 or 512, and tuning `num_chunks` upward if memory allows should improve silhouette fidelity and small-structure geometry, though with a real cost in VRAM and decode time. The next quality lever is **texture sampling resolution and scheduler choice**. The graph currently samples multiviews at 512 with 25 steps and then upscales them mostly by plain resize before baking. A stronger configuration would keep the same camera logic but either increase sampling steps, try alternative schedulers and sigma modes through `Hy3DDiffusersSchedulerConfig`, or enable the muted learned upscaler path instead of relying on simple resize. Right now, node 118 exists but is not active, so the bake stage is getting larger images, not genuinely more detailed ones. fileciteturn0file0 citeturn39view0turn39view1turn39view2

The main runtime bottlenecks are predictable from both code and field reports. Shape decode gets heavier with higher octree resolution and chunk count. Texture generation has to run a 2.5D diffusion UNet plus renderer passes, and the official 2.1 materials note that texturing is substantially more memory-hungry than shape alone. The final repair stage can also become the long pole when the baked mask is large; Tencent’s own 2.1 issue tracker has reports of the texture inpainting stage becoming extremely slow when big regions must be filled. In other words, the expensive parts are not just “diffusion” broadly, but specifically **mesh decode**, **multi-view render/bake**, and **large-hole inpainting**. citeturn28search1turn30search1turn27search0

Several nodes can be skipped or simplified depending on the input regime. If the source views are already clean RGBA cutouts, the workflow’s own note says the background-removal plus invert/join branch is unnecessary. If the lighting is already neutral, delighting may be optional; if the delight model starts flattening material cues too aggressively, skipping it can preserve surface identity. For fast draft runs, you can also stop after `Hy3DBakeFromMultiview` or after `Hy3DMeshVerticeInpaintTexture`, accepting more UV holes in exchange for speed. Conversely, if quality matters more than speed, those inpaint passes are exactly the ones you should keep. fileciteturn0file0 citeturn18view0turn20view3turn30search1

The last optimization is strategic rather than parametric: decide whether you want to stay in the **explicit v2.0-style graph** or migrate toward the **2.1-style higher-level pipeline**. The provided visualbruno repo bundles paint generation, bake, and inpaint more tightly and extends them toward production-ready PBR material synthesis, which is better if your goal is albedo plus material channels. But this exact saved JSON is naturally aligned with Hunyuan3D-2mv plus the older v2.0 Delight/Paint nodes, and the official 2.1 codebase itself has documented multiview-version skew.
